## Protocolo de ejecución para Tierra High

Este protocolo elimina ambigüedades para que quien retome no tenga que inferir ni volver a investigar decisiones ya tomadas.

1. Abrir `PROGRESS.md`, este complemento, `docs/qa/2026-09-10-prepublication-review.md` y el plan visual de 2026-09-05. Inspeccionar `git status --short` y no restaurar, limpiar ni reformatear cambios ajenos: el checkout está deliberadamente sucio.
2. Trabajar en el orden A → B → C → D → E. Antes de cada punto, localizar la prueba o crear una prueba mínima que falle por el defecto exacto. Ejecutar solo esa prueba; implementar el cambio mínimo; repetir prueba, typecheck y lint. No cerrar una casilla por inspección del código ni por una prueba vecina.
3. Cuando un paso proponga archivos candidatos, comprobar primero si una primitiva equivalente ya existe. Reutilizarla si respeta el contrato; si no, crear una unidad pequeña con una sola responsabilidad. No duplicar listas de países, reglas de correo, parseadores de monto ni cálculo de posicionamiento de ayudas en formularios.
4. Mantener datos operativos en IndexedDB. Preferencias efímeras pueden usar el mecanismo aprobado, pero ninguna lista, teléfono, importe, historial o borrador de CRM debe migrar a Local Storage. Todo cambio de contrato persistido exige versión, migración aditiva, compatibilidad de respaldo y prueba de round-trip antes de marcarse.
5. Cambios destructivos, archivos, restauración, aplicación de actualización y salida con borrador usan una confirmación visual alineada a los componentes existentes. No mostrar confirmación por pulsaciones, filtro, navegación inocua ni edición de texto; sí cuando se pueda perder o transformar información. Nunca sustituir eliminación por archivo de forma oculta.
6. Al terminar cada tramo, ejecutar las pruebas del tramo, `npm run typecheck`, `npm run lint`, `npm run build` y un preview con datos sintéticos. Documentar archivo, comando, conteo, fecha y resultado en `VERIFIER.md`; actualizar `PROGRESS.md` solo con evidencia que realmente pasó. La revisión final E corre la suite completa, E2E, auditoría, `git diff --check`, teclado, foco, ES/EN, zoom real 100/200 % y capturas; sin esos resultados no se propone publicar.

### Contrato P1 — selector de país según contexto

1. `CountryPicker` recibe `optionPresentation: 'country' | 'phone'`, con `country` como valor predeterminado para compatibilidad.
2. En residencia y todo campo de ubicación, cada opción y valor seleccionado se presenta sólo como nombre localizado del país. Se persiste el ISO existente; los valores históricos libres siguen legibles y no se recodifican.
3. En `PhoneField`, cada opción y valor seleccionado se presenta exactamente como `País (ISO), +código`, por ejemplo `México (MX), +52`. El prefijo continua independiente de residencia y no se infiere por geolocalización.
4. La lista filtra por nombre ES/EN, ISO y lada, con teclado existente; no se consulta red ni se almacena información adicional.

### Contrato P2 — descarte coherente de capas flotantes

1. Crear/reutilizar un único hook `useDismissibleLayer` que escucha `pointerdown` sólo mientras la capa esté abierta y descarta únicamente si el objetivo está fuera de la raíz que contiene disparador y capa.

3. Un clic exterior cierra la capa y permite que el foco nativo llegue al control clicado. Escape y navegación de teclado preexistentes se conservan.
4. No aplicar la regla a `FilterBar` ni `AccordionSection`: son divulgaciones persistentes de información de trabajo, no popovers; cerrarlas al avanzar por el formulario perdería contexto.
5. Pruebas obligatorias: lista de países, calendario, búsqueda, notificaciones y menú de acciones desaparecen al clicar otro campo; una opción de país y una acción del menú siguen ejecutándose al clicar dentro.

### Contrato P3 — geometría estable de formulario Lead

1. `form-grid` alinea sus hijos al inicio de cada fila. Un textarea alto no estira visualmente al input/selector de la columna vecina; Correo conserva altura de control simple junto a Nota comercial.
